# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

StudyScope ist eine Desktop-Lernsoftware für Windows und Linux (Photino.Blazor 4) für Dokumenten-Chat (RAG) und automatische Karteikarten-Generierung aus eigenen Unterlagen (`.pdf`, `.txt`, `.csv`). KI-Anbindung wahlweise lokal (Ollama, LM Studio) oder über Cloud-Dienste (Gemini, OpenAI, Mistral, beliebige OpenAI-kompatible Endpunkte). Code, Kommentare und UI-Texte sind auf Deutsch.

## Befehle

Alle Projekte zielen auf `net10.0`. Solution-Datei ist `StudyScope.slnx`. Unter Linux braucht Photino 4 zusätzlich WebKitGTK **4.1** (`libwebkit2gtk-4.1.so.0`), GTK 3 und libnotify. Photino 3.x war gegen WebKitGTK 4.0 gelinkt, das ab Ubuntu 24.04 fehlt – nicht auf 3.x zurückgehen. Alle Photino-Projekte (UI und Setup) müssen dieselbe Photino.Blazor-Version nutzen.

```bash
dotnet build StudyScope.slnx
dotnet run --project StudyScope.UI
dotnet test StudyScope.Tests
dotnet test StudyScope.Tests --filter "FullyQualifiedName~LlmServiceDispatcherTests"   # eine Testklasse
dotnet test StudyScope.Tests --filter "Name=MethodenName"                              # ein einzelner Test
dotnet publish StudyScope.UI -c Release -r win-x64                                     # Release-Build (siehe Properties/PublishProfiles)
.\build\build-setup.ps1 -Runtime all          # Installationsprogramme nach artifacts/ (setup.exe, linux-x64.tar.gz)
./build/build-setup.sh all                     # dasselbe unter Linux
.uilduild-setup.ps1 -OutputDirectory <ordner>   # Prüfbau, ohne Pakete in artifacts/ zu überschreiben (Linux: STUDYSCOPE_ARTIFACTS_DIR=<ordner>)
```

Tests: NUnit 4 + Moq, Oberflächensprache in allen Tests `de-DE` (siehe „Mehrsprachigkeit“). Die Versionsnummer steht zentral in `Directory.Build.props` (gilt für App und Setup).

Testdaten: In Tests nur eindeutig erfundene Werte verwenden, die nicht wie echte API-Keys aussehen (z. B. `"DUMMY_TEST_KEY_…"`, nie `AIza…`, `sk-…` o. Ä.), damit GitHubs Secret-Scanning nicht anschlägt. Ebenso neutrale Profilnamen wie „Testprofil“ statt Namen echter Profile; nie echte Dokumente oder Benutzerdaten ins Repository legen.

## CI

`.github/workflows/ci.yml` (GitHub Actions) bei Pull Requests nach master, Push auf master und manuell: Matrix `windows-latest`/`ubuntu-latest`, .NET 10 (`global.json`: SDK 10.0.x mit `rollForward: latestFeature`), NuGet-Cache, `dotnet build -c Release` (Warnungen als Hinweis, kein Fehler), Tests mit trx-Artefakt und Zusammenfassung, unter Linux ein zweiter Testlauf mit `STUDYSCOPE_TEST_CULTURE=de-DE` (Dezimalkomma; die Runner selbst laufen mit en-US bzw. invarianter Kultur) (`.github/scripts/test-summary.ps1`). Installiert ffmpeg (Linux apt; Windows fest versionierter Gyan-Build aus GitHub-Releases mit SHA-256-Prüfung und Cache, `FFMPEG_WINDOWS_VERSION`/`FFMPEG_WINDOWS_SHA256` zusammen anheben, Chocolatey nur als Rückfall) sowie unter Linux nur `fontconfig` + `fonts-dejavu-core` für SkiaSharp – WebKitGTK/GTK/libnotify braucht die CI nicht, weil die Tests kein Photino einbinden. In der CI gilt `STUDYSCOPE_REQUIRE_INTEGRATION=1`: Tests, die ffmpeg oder SkiaSharp brauchen, rufen `IntegrationRequirement.Unavailable(grund)` (Tests/Common) statt `Assert.Ignore` – lokal übersprungen, in der CI ein Fehler. Job „Installationspaket“ nur bei Push auf master/manuell, beim Release und in PRs von `release/*`-Branches: Build-Skripte mit `STUDYSCOPE_ARTIFACTS_DIR` im Temp-Ordner des Runners, Pakete 7 Tage als Artefakt. Läuft ein Test in der CI nur gelegentlich schief, den Test stabil machen statt Wiederholungen einzubauen.

Release: `.github/workflows/release.yml` bei einem Tag `v*`. `.github/scripts/release-check.ps1` bricht ab, wenn der Tag nicht `v<Version>` aus `Directory.Build.props` ist, nicht auf einem Commit in master steht oder `CHANGELOG.md` keinen Abschnitt `## [<Version>]` hat; danach ruft der Workflow `ci.yml` (`workflow_call`, Ereignis bleibt „push“ → Paket-Job läuft), `release-notes.ps1` baut den Text (CHANGELOG-Abschnitt über `changelog-section.ps1`, Installationshinweise mit SmartScreen und ffmpeg optional, Prüfsummen, `SHA256SUMS.txt`), zusätzlich Kopien ohne Versionsnummer `StudyScope-Setup.exe`/`StudyScope-linux-x64.tar.gz` für dauerhafte Links `…/releases/latest/download/<Datei>` (README „Download-Links“; funktionieren nur für das veröffentlichte „Latest“-Release, nicht für Entwürfe), und nur der Job „Release-Entwurf“ hat `contents: write` und legt per `gh release create --draft` an – nie über ein vorhandenes Release. Achtung PowerShell: „“ gelten in Strings als Anführungszeichen – in Meldungen der Skripte '…' verwenden. Die CI nutzt PowerShell 7: in `build-setup.ps1` Argumente wie `"-p:Name=Wert"` immer quoten (über `@args` weitergereicht zerlegt pwsh 7 sie sonst, MSB1008) – lokal mit Windows PowerShell 5.1 fällt das nicht auf. Neue Version: `Directory.Build.props` (Version, AssemblyVersion, FileVersion) und `CHANGELOG.md` (Änderungen sammeln sich bis zum Release unter `## [Unveröffentlicht]`, beim Release wird daraus `## [<Version>] – <Monat>`); alles andere (Info-Dialog, Setup, Apps & Features, Manifest) liest `AppInfo.Version`. Die „1.0.3“ in den Setup-Tests sind erfundene Testwerte.

## Architektur

Schichtenaufbau mit Abhängigkeiten nur nach innen:

- **StudyScope.Core** – `Common/AppPaths` (gemeinsame Pfade, z. B. Benutzerdaten-Ordner), Interfaces (`ILlmService`, `IStorageService`, `IDocumentService`, `IEncryptionService`, …) und Modelle (`AiConfig` mit `AiProviderType`-Enum, `UserProfile`, `DocumentItem`, `Flashcard`, `ChatMessage`), `Localization/` (Sprache, ICU-Formatierung, Sprachdaten). Einzige Abhängigkeit: das Paket MessageFormat (MIT, ohne eigene Abhängigkeiten) für CLDR-Pluralregeln.
- **StudyScope.Infrastructure** – Implementierungen. Achtung: Ordner heißt `Service/`, der Namespace aber `StudyScope.Infrastructure.Services`.
- **StudyScope.ViewModels** – ViewModels mit handgeschriebenem `INotifyPropertyChanged` (CommunityToolkit.Mvvm ist referenziert, wird aber nicht genutzt).
- **StudyScope.UI** – Photino.Blazor-Host. `Program.cs` ist der DI-Composition-Root (alles als Singleton). Razor-Komponenten in `Components/` injizieren ViewModels per `@inject`, abonnieren `PropertyChanged` und rufen `StateHasChanged` auf (Abmeldung in `Dispose`). Native Dateidialoge laufen über die statische Klasse `DesktopDialogs` (`MainWindow` wird in `Program.cs` gesetzt). Dateipfade zu Programmdateien immer über `AppContext.BaseDirectory` bilden, nie relativ zum Arbeitsverzeichnis.

- Sprache (3b-3): Das Setup folgt der Systemsprache (`SetupLanguage.Apply` ganz am Anfang von `Main`: `CultureInfo.InstalledUICulture`, übersetzt → diese Kultur, sonst Englisch; `STUDYSCOPE_UI_CULTURE` erzwingt eine Sprache), ohne Auswahl im Assistenten und ohne Eintrag in den Benutzerdaten. Texte in `SetupCoreStrings` (Setup.Core: Ordnerprüfung, Fortschritt, Fehler, Verknüpfungen, `.desktop`-Eintrag, Voraussetzungen) und `SetupStrings` (Setup: Assistent, Fenstertitel, `NativeMessage`, Ordnerdialog), HTML-Texte über `StudyScope.Setup.Resources.LocHtml`. Weil die setup.exe eine Einzeldatei ist (Satellitenassemblies im Bündel), prüft `SetupLanguage.HasTexts` per `Assembly.GetSatelliteAssembly` statt über Ordner – nicht über `ResourceManager.GetResourceSet(…, tryParents: false)`, das nach einem Rückfall die neutrale Fassung unter der angefragten Kultur zwischenspeichert. `lang`/`dir` setzt `App.razor` per JS-Interop (`SetupContext.LanguageTag/Direction`), `index.html` hat keine feste Sprache. Linux-Menüeintrag (`GenericName`, `Comment`, `Keywords`, Aktion „Deinstallieren“) und Beschreibung der Windows-Verknüpfung in der Sprache des Setups; „Apps & Features“ (Anzeigename, Herausgeber) bleibt sprachneutral. `setup.css` mit logischen Eigenschaften. `install.sh`: Ausgaben über `msg "<Deutsch>" "<English>"`, Deutsch bei `LC_ALL`/`LC_MESSAGES`/`LANG` mit „de…“ (in dieser Reihenfolge), sonst Englisch, keine Zusatzdateien; LF-Zeilenenden. Tests: `Localization/SetupLocalizationTests` (Sprachwahl, Meldungen en, `.desktop`, keine Umlaut-Texte im Setup-Code, `install.sh`).

### Photino-Eigenheiten (gelten für jedes Photino-Projekt, auch das Setup)

- Dateifilter für `ShowOpenFile`/`ShowSaveFile` immer über `FileDialogFilters.ForPhotino(filters, OperatingSystem.IsLinux())` übergeben: Photino.Native unter Linux zerlegt Filter mit mehreren Endungen falsch und zeigt sonst keine Dateien an.
- Nach `Build()` `app.MainWindow.SetLogVerbosity(0)` setzen, sonst flutet Photino unter Linux die Konsole.
- Zoom des WebViews nur über `PhotinoWindow.Zoom`/`SetZoom` (Prozent; Windows WebView2 `ZoomFactor`, Linux WebKitGTK `zoom-level`). Photino hat kein Ereignis für Zoomänderungen und keinen Schalter für den eingebauten WebView2-Zoom (`IsZoomControlEnabled`/`AreBrowserAcceleratorKeysEnabled` bleiben an). Aufruf direkt aus Blazor-Ereignissen ist in Ordnung (in der Sandbox mit echten Eingaben geprüft). Startwert vor `Run` über `app.MainWindow.Zoom` (wird nach dem Laden angewendet, kein Aufblitzen); unter Windows vor dem Erzeugen des WebViews kein `SetZoom`/`Zoom` lesen (keine Null-Prüfung in Photino.Native).
- Profilnamen werden zu Dateinamen: Prüfung über `ProfileNameValidator` (Core, im ViewModel), Absicherung des Pfads in `JsonStorageService.ToSafeProfileFileName`.

### KI-Anbindung

`LlmServiceDispatcher` ist die einzige `ILlmService`-Implementierung im Betrieb: Bei jedem Aufruf lädt er die `AiConfig` des **aktiven Profils** (`last_profile.txt` → `LoadAiConfigForProfileAsync`, dieselbe Quelle wie die Statusleiste; nur wenn das Profil gar keine Einstellung hat, die globale `config.json`) und verzweigt per `switch` auf `SelectedProvider` (Ollama nativ, Gemini nativ, Mistral, sonst OpenAI-kompatibler Pfad für LM Studio/OpenAI/Custom). Ein neuer Provider braucht: Enum-Wert in `AiConfig.cs`, Fälle in `AskQuestionAsync` **und** `ValidateConnectionAsync`, sowie UI in `SettingsModal.razor`/`SettingsViewModel`. `FakeAi` ist der Standard-/Testmodus und liefert für Karteikarten-Prompts (enthält „Lernkarteikarten“ oder „JSON“) ein festes JSON-Array.

- Fehler des Dienstes (HTTP-Status, Netzwerk, Zeitüberschreitung, unerwartete Antwort) wirft der Dispatcher als `LlmServiceException` (Core/Common, `Message` ist ein deutscher Satz mit Handlungsempfehlung je Status, technische Antwort in `Detail`) – **nie** als Antworttext, sonst werten die Dienste die Fehlermeldung als Inhalt aus. Nur ein Abbruch durch den Benutzer liefert `LlmServiceDispatcher.CancelledResponse`. Die ViewModels zeigen `ex.Message` an; `LocalLlmDiscoveryService` meldet HTTP-Fehler der Cloud-Modellabrufe ebenso.
- Sprache der KI-Ergebnisse (3c-1): Einstellung `OutputLanguage` (Core/Localization) als Text – „ui“ (wie Oberfläche, Standard), „documents“ (Erkennung über `LanguageGuess`: nur Stoppwörter, die allein in einer Sprachliste stehen; unsicher → Oberfläche) oder ein Kulturname; wählbar nur Sprachen der Oberfläche. Gespeichert je Profil (`UserProfile.OutputLanguage`) und global (`UiSettings.OutputLanguage`), `IStorageService.Load/SaveOutputLanguageAsync` (Profil → global → „ui“); neue Profilfelder auch in `JsonStorageService.WriteProfileFileAsync` übernehmen, sonst gehen sie beim nächsten Speichern verloren. Die ViewModels holen die Einstellung über `IOutputLanguageProvider` (optionaler Konstruktorparameter bzw. `OutputLanguageProvider`) und geben sie jeder Erzeugen-Methode als `string? outputLanguage` mit (vor dem `CancellationToken`). Die Dienste lösen sie auf den ausgewählten Textstellen auf (`ResultLanguage.Resolve`), ersetzen die frühere feste Angabe durch genau eine Sprachzeile am Prompt-Ende (`ResultLanguage.ApplyToPrompt` → `OutputLanguage.PromptLine`, z. B. „Sprache der Antwort: Englisch (English). Alle Texte … in dieser Sprache …“) und speichern den Code am Ergebnis (`Language` an Mindmap, Präsentation, Quizfrage, Karteikarte, Datentabelle, Bericht, Audio, Video; ältere Daten: null). Feste Inhalte, die der Code erzeugt (Rückfall-Titel, „Wahr/Falsch“, Präsentation aus der Mindmap), stehen in `ContentStrings` (Infrastructure) und werden mit `ResultLanguage.Content(sprache, …)` in der Ergebnissprache gelesen. Ergänzen behält die Sprache des Vorhandenen (Quizfragen eines Themas, weitere Tabellenzeilen, Video aus einer Präsentation, Präsentation aus der Mindmap, Karteikarten: Mehrheit des Stapels). Chat: `ChatViewModel.WithLanguageLine` hängt die Zeile nur bei nicht-deutscher Ergebnissprache an die Frage, der Dispatcher wählt danach `RagSystemPromptFor` (Beispielsatz „steht nicht in den Unterlagen“ in der Ergebnissprache); `ILlmService` bleibt unverändert. ### Websuche (Phase 4: 4-1 Dienste und Einstellungen, 4-2 Chat)

- Grundsatz: Ins Netz geht nur Text, den der Benutzer selbst eingegeben hat – nie Auszüge, Dateinamen, Profilnamen, Knotentitel, Themenvorschläge oder KI-Text. Einziger Weg zu einer Anfrage ist `WebSearchQuery.FromUserQuestion` (Core/Models/WebSearch.cs; Steuerzeichen/Umbrüche → Leerzeichen, ≤ 400 Zeichen an einer Wortgrenze) bzw. `WebSearchQuery.ConnectionTest()` („StudyScope“ für „Verbindung testen“); kein öffentlicher Konstruktor (Test). Fragen aus der Mindmap („Im Chat erklären lassen“) lösen nie eine Websuche aus (4-2). Web-Inhalte werden nie gespeichert.
- `IWebSearchService` (Core) → `WebSearchDispatcher` (Infrastructure/Service/WebSearch, einzige Implementierung im Betrieb): lädt bei jedem Aufruf `WebSearchSettings`, wählt `TavilySearchService` (POST https://api.tavily.com/search, Header `Authorization: Bearer`, `search_depth: basic` = 1 Credit, ohne `include_answer`/`raw_content`, kein `max_age_hours` – HTTP 434 im Gratis-Tarif) oder `SearxngSearchService` (GET `<Adresse>/search?format=json&q=…&language=<Ergebnissprache>`; 403 → Hinweis „JSON-Format in settings.yml freischalten“). `STUDYSCOPE_FAKE_WEBSEARCH=1` schaltet nur für Prüfungen `FakeWebSearchService` ein (example.org, de/en, kein Netz) – nie über die Einstellungen. Ohne eingerichteten Dienst `WebSearchException.NotConfigured`.
- Fehler als `WebSearchException` (Core/Common, wie `LlmServiceException`: Satz + Handlungsempfehlung aus `CoreStrings.WebSearch_*`, technische Antwort in `Detail`): 401/403 Schlüssel, 429 zu viele Anfragen, 432 Monatskontingent/Tarifgrenze, 433 Pay-as-you-go-Grenze, 5xx, Netzwerk, Zeitüberschreitung (eigenes Zeitlimit 15 s je Anfrage in `WebSearchHttp.SendAsync`; Abbruch durch den Benutzer bleibt `OperationCanceledException`). `WebSearchHttp.Clean` lässt nur http/https-Treffer ohne Benutzerdaten durch (`ExternalUrl`), entfernt doppelte Adressen, Steuerzeichen und Umbrüche, kürzt Titel (200) und Ausschnitt (1.500).
- Speicherung: `WebSearchSettings` (Anbieter als Text, `TavilyApiKey` verschlüsselt wie die anderen Schlüssel, `SearxngUrl`, `MaxResults` 1–10, Standard 5) global in `config.json` unter `WebSearchSettings`; `SaveAiConfigAsync` behält den Knoten. Je Profil `UserProfile.WebSearchEnabled` (Standard false) und `WebSearchNoticeAcceptedFor` (Dienst, für den der Hinweis bestätigt wurde; bei Anbieterwechsel erneut) über `Load/SaveWebSearchStateAsync` – **ohne** globalen Rückfall, ein neues Profil sucht nie im Internet. Beide Felder stehen in `WriteProfileFileAsync`.
- Einstellungen › „🌐 Websuche“ (`WebSearchSettingsSection.razor`, `WebSearchSettingsViewModel`, Menü `settings:websearch`): Dienst, Schlüssel bzw. ### Export über ffmpeg (MP4, MP3)

- ffmpeg wird **nicht** mitgeliefert (optionale Voraussetzung, in README, Setup-Willkommensseite und `install.sh` als Hinweis). `IFfmpegService` (Core) / `FfmpegService` (Infrastructure): `GetStatusAsync` (zwischengespeichert, `refresh` sucht neu), `TestAsync(path)` ohne Speichern, `RunAsync(args, total, progress, ct)`. `FfmpegStatus` (Core/Models/ExportSettings.cs) mit `HasH264`/`HasAac`/`HasMp3` aus `ffmpeg -encoders`, deutscher Meldung und Installationshinweis (`FfmpegInfo`: `winget install Gyan.FFmpeg`, `sudo apt install ffmpeg`).
- Suche `FfmpegLocator` (Dateisystem/Umgebung austauschbar, ohne ffmpeg testbar): eigener Pfad (Datei oder Ordner, auch `…\bin`) → PATH → Windows: `%LOCALAPPDATA%\Microsoft\WinGet\Links`, WinGet-Paketordner `*FFmpeg*\*\bin`, Program Files, Chocolatey, Scoop, `C:\ffmpeg\bin`; Linux: `/usr/bin`, `/usr/local/bin`, `/snap/bin`. Der Pfad steht global in `config.json` unter `ExportSettings` (`LoadExportSettingsAsync`/`SaveExportSettingsAsync`; `SaveAiConfigAsync` behält `SpeechSettings` **und** `ExportSettings`). Einstellungen › „🎞️ Export“ (`ExportSettingsSection.razor`, `ExportSettingsViewModel`): Pfad, „ffmpeg suchen/testen“, Installationsanleitung; nach dem Schließen prüfen Audio, Video und Bericht neu.
- Prozess: immer `ProcessStartInfo.ArgumentList` (nie ein zusammengesetzter String), `-nostdin -y -loglevel error -progress pipe:1`, Fortschritt aus `out_time_us`/`out_time`, Fehlerausgabe (letzte 40 Zeilen) in `FfmpegException.Detail`, Abbruch per `Kill(entireProcessTree)` → `OperationCanceledException`. Ausgaben immer erst temporär (`<Ziel>.part` bzw. `.<Name>.part` im Zielordner, Format per `-f`), dann `File.Move`; temporäre Dateien in `finally` löschen. Argumente baut `FfmpegArguments` (testbar): `Mp3` (libmp3lame, 64 kbit/s mono), `Mp4` (concat-Demuxer, libx264 veryfast/stillimage/crf 22, yuv420p, 25 Bilder/s, AAC 96 kbit/s mono oder `-an`, `-t` exakte Dauer, `+faststart`), `ConcatList` (Dauer mit Punkt, letztes Bild ohne Dauer wiederholt).

### Persistenz

`JsonStorageService` speichert unter `AppPaths.UserDataDirectory` (Windows `%APPDATA%\StudyScope\`, Linux `~/.config/StudyScope/`): je Profil `Profiles/<name>.json` (Dokumente + profilspezifische `AiSettings`), dazu `config.json` (globale KI-Konfiguration) und `last_profile.txt`. API-Keys werden in Profilen **und** in `config.json` beim Schreiben per `AesEncryptionService` (AES-GCM, fest abgeleiteter Schlüssel) verschlüsselt und beim Lesen entschlüsselt; im Speicher sind sie immer Klartext. Profile daher nur über `WriteProfileFileAsync` schreiben (verschlüsselt eine Kopie), nie das gelesene Objekt direkt serialisieren. Alter Klartext und früher doppelt verschlüsselte Keys bleiben lesbar (`DecryptApiKey`). `SettingsViewModel` prüft die Formularwerte per `ValidateConnectionAsync(config)` und speichert sie danach profilspezifisch (maßgeblich) und global (Rückfall). Profile ohne eigene Einstellung stehen auf dem Standard „Fake-KI (Testmodus)“ und nutzen diese auch.

Für Tests nimmt `JsonStorageService` ein Basisverzeichnis entgegen (`new JsonStorageService(tempDir)`); Tests nutzen ein temporäres Verzeichnis, nicht `%APPDATA%`. Für Oberflächentests der laufenden App lenkt die Umgebungsvariable `STUDYSCOPE_USER_DATA_DIR=<ordner>` `AppPaths.UserDataDirectory` (und damit alle Dienste samt Karteikarten) in einen Sandbox-Ordner um.
